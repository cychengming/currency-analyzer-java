## 一、集合：HashMap（源码级）

**Q1. 默认容量、负载因子、树化阈值分别是多少？**

| 项 | 值 | 源码位置 |
|---|---|---|
| `DEFAULT_INITIAL_CAPACITY` | `1 << 4` = **16** | HashMap.java:238 |
| `DEFAULT_LOAD_FACTOR` | **0.75** | HashMap.java:250 |
| `TREEIFY_THRESHOLD` | **8** | HashMap.java:260 |
| `UNTREEIFY_THRESHOLD` | **6** | HashMap.java:267 |
| `MIN_TREEIFY_CAPACITY` | **64** | HashMap.java:275 |

要点：
- 树化条件：链表长度 ≥ 8 **且** 数组长度 ≥ 64；数组没到 64 时先 `resize()`——源码 `if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY) resize();`（HashMap.java:789）
- 阈值 8 的来历：源码注释写明，随机 hashCode + 0.75 负载因子下桶内节点数服从 **λ≈0.5 的泊松分布**，注释给的 8 对应概率是 `0.00000006`；我用 `exp(-0.5)*0.5^8/8!` 复算 = **5.876e-08**，吻合
- 所以树化是**防御性设计**（防哈希碰撞攻击把查询打成 O(n)），不是常规路径

**Q2. 为什么容量必须是 2 的幂？扩容时为什么不重算 hash？**

要点（全部源码可查）：
- 下标计算 `(n - 1) & hash`（`tab[i = (n - 1) & hash]`），n 为 2 的幂时等价于取模且分布无空洞
- `tableSizeFor()` 把入参向上取到 2 的幂：`n = -1 >>> Integer.numberOfLeadingZeros(cap - 1)`
- 扰动函数：`hash(key) = (h = key.hashCode()) ^ (h >>> 16)`，让高 16 位参与低位运算（HashMap.java:336-339）
- 扩容迁移用 `(e.hash & oldCap) == 0` 判断：等于 0 留原下标 j，否则去 `j + oldCap`（resize 里的 loHead/hiHead 分支）——因为 oldCap 是 2 的幂，这一位正好区分「原位」和「原位 + oldCap」，**无需重算 hash**

追问：JDK8 头插改尾插解决了并发扩容成环，但 HashMap 依然非线程安全（并发 put 仍会丢数据）。

> 来源：[OpenJDK HashMap.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/HashMap.java)

## 二、集合：ArrayList

**Q3. 默认容量是 10 吗？什么时候分配？扩容多少？**

要点：
- `DEFAULT_CAPACITY = 10`（ArrayList.java:119），但 `new ArrayList<>()` 建的是空数组，**首次 add 才扩到 10**（源码注释：*will be expanded to DEFAULT_CAPACITY when the first element is added*）
- 扩容：以 `oldCapacity >> 1` 为 preferred growth，即 **1.5 倍**，再 `Arrays.copyOf`（ArrayList.java:232-241）
- `new ArrayList<>(n)` 直接按 n 分配，省掉多次拷贝
- 删除元素不缩容

追问：为什么 1.5 倍不是 2 倍？（空间/时间折中——这是设计权衡的通行解释，JDK 源码**没写理由**，别说成"源码说"）

> 来源：[OpenJDK ArrayList.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/ArrayList.java)

## 三、集合：ConcurrentHashMap 1.7 vs 1.8

**Q4. 1.8 相比 1.7 改了什么？**

要点（源码对照）：
- 1.7：`Segment<K,V> extends ReentrantLock` + `Segment<K,V>[] segments` + `segmentShift/segmentMask` 定位分段 → 分段锁
- 1.8：无分段锁。空桶用 `casTabAt` 无锁 CAS 插入；有冲突时 `synchronized (f)` 直接锁**桶的头节点**；计数用 `baseCount` + `CounterCell[]` 分散竞争
- 1.8 里**仍保留** `static class Segment`，但注释写明：*Stripped-down version of helper class used in previous version, declared for the sake of serialization compatibility* —— **只为序列化兼容，不参与并发控制**

追问：为什么桶级锁并发度更高？（锁粒度从"段"降到"桶"；扩容时多线程可协助迁移）

## 四、Java 基础：数值转换与精度

**Q5. 自动转换（widening）真的「无精度损失」吗？**

**不完全是。** JLS §5.1.2 把 19 种 widening primitive conversion 分两类：

- **值精确保留**：整型之间；byte/short/char → 浮点；int → double；float → double
- **可能丢精度**：`int → float`、`long → float`、`long → double`（原文：*may result in loss of precision, that is, the result may lose some of the least significant bits*；但按 round-to-nearest 正确舍入，且**永不抛运行时异常**）

> ⚠️ 我上一版写「小→大无精度损失」是错的：`int → float` 也会丢尾数（float 只有 24 bit 有效位）。

**Q6. 强制转换的规则？`(int) 3.99` 等于多少？**

- 浮点 → 整型：**向零截断**，`(int) 3.99 == 3`（JLS §5.1.3；Python 复算 `int(3.99)=3` 一致）
- `Math.round(3.5) = 4`、`Math.round(-3.5) = -3`（javadoc：*ties rounding to positive infinity*，朝 +∞ 取整，不是四舍五入）
- `round(double) → long`，`round(float) → int`

**Q7. 三元表达式 `true ? 1 : 'a'` 的类型是什么？**

**是 `char`，不是 `int`。** JLS §15.25.2 规则：一边是 T（byte/short/char），另一边是**可表示为 T 的 int 常量表达式**时，整体类型就是 T → 结果 `'\u0001'`。

危险变体：`Integer x = null; int y = flag ? x : 0;` —— 一边 `int`、一边 `Integer` 时按"装箱 T ↔ 原始 T"规则整体为 `int`，于是**对 null 拆箱 → NPE**。

> ⚠️ 我上一版写「自动提升为 int」，错了。

**Q8. Integer 缓存范围？BigDecimal 为什么用 String 构造？**

- `Integer` 缓存 **-128 ~ 127**（源码注释：*Cache to support the object identity semantics of autoboxing for values between -128 and 127 (inclusive) as required by JLS*）→ 区间内 `==` 为 true，区间外 false
- `new BigDecimal(0.1)` 的 javadoc 原文：*The results of this constructor can be somewhat unpredictable*；实际值 = `0.1000000000000000055511151231257827021181583404541015625`
- 浮点验证：`0.1 + 0.2 = 0.30000000000000004`，与 0.3 差 `5.55e-17`（Python 与 Java double 同为 IEEE 754 binary64，结果一致）

> 来源：[JLS §5.1.2/§5.1.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-5.html)、[JLS §15.25](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html)、[Integer.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/Integer.java)、[BigDecimal.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/math/BigDecimal.java)、[Math.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/Math.java)

## 五、并发：sleep / wait / join

**Q9. 三者的区别？wait 为什么定义在 Object 上？**

| | `Thread.sleep` | `Object.wait` | `Thread.join` |
|---|---|---|---|
| 是否释放 monitor | **不释放** —— javadoc：*The thread does not lose ownership of any monitors* | **释放** | 释放的是**目标 Thread 对象**的 monitor |
| 前置条件 | 无 | 必须持有该对象 monitor，否则 `IllegalMonitorStateException`（javadoc @throws 原文） | 无 |
| 唤醒 | 超时 / interrupt | notify / notifyAll / 超时 / **虚假唤醒** | 目标线程终止 |
| 定义在 | Thread（static） | Object | Thread |

**wait 为什么在 Object 上**：JLS §17.1 原文——*Each object in Java is associated with a monitor, which a thread can lock or unlock*。锁的载体是对象（monitor），等待/通知自然也要挂在对象上；若放进 Thread，就只有"以线程为锁"这一种互斥模型了。

**join 的实现**（源码）：`join()` → `join(0)`；`join(long millis)` 内部是
```java
synchronized (this) { while (isAlive()) { wait(0); } }
```
→ join 本质是用**目标线程对象**当锁做 wait 循环。⚠️ 精确说法：它只释放目标 Thread 对象的 monitor，**当前线程持有的其他锁不会释放**（笼统说"join 释放锁"在追问里会翻车）。

**为什么用 while 包 wait**：javadoc 明确把 *Thread T is awakened spuriously* 列为唤醒原因之一，并要求循环判断 → 不能用 `if`。

> 来源：[Thread.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/Thread.java)、[Object.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/Object.java)、[JLS §17.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html)

## 六、并发：volatile 的内存语义

**Q10. volatile 保证了什么？**

1. **可见性 / 一致性**：JLS §8.3.1.4 原文——*A field may be declared volatile, in which case the Java Memory Model ensures that all threads see a consistent value for the variable*
2. **顺序性**：happens-before 是「program order + synchronizes-with 的传递闭包」（§17.4.5 原文：*The happens-before order is given by the transitive closure of synchronizes-with edges and program order*）
3. **复合操作仍不安全**：§8.3.1.4-1 的例子只保证同一线程内 `i++` 与 `j++` 两次写的顺序（所以不会看到 j > i），但两个读之间可能插进别的线程的执行 —— `i++` 这类复合操作要 `AtomicInteger` 或加锁。⚠️ 这是结构性推论，JLS 没有这句原话，面试可讲逻辑但别引成"原文"

追问：DCL 单例为什么加 volatile？（防"分配内存→赋引用→初始化"重排导致半初始化对象逸出——JSR-133 层级结论，**未核到规范原文**，见核验表）

> 来源：[JLS §8.3.1.4](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html)、[JLS §17.4](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html)

## 七、分布式事务

**Q11. RocketMQ 事务消息的流程？**

官方文档流程（逐句可查）：
1. Producer 发消息 → Broker 保存但**不投递**，该状态叫 **half message**
2. Broker 回 ACK → Producer 执行本地事务 → 发第二次 ACK（Commit / Rollback）
3. Commit → half message 标记可投递；Rollback → 回滚且不投递
4. 若断网/Producer 重启导致**没收到第二次 ACK**、或状态为 Unknown → Broker 等一段时间后**回查** Producer 集群里任一生产者询问状态

**Q12. Seata AT 模式的机制？全局锁何时拿？**

官方文档要点：
- 是 **2PC 的演进**：一阶段在同一个本地事务里提交「业务数据 + 回滚日志(rollback log)」，然后释放本地锁和连接；二阶段 Commit 异步快速完成，Rollback 则基于一阶段日志补偿
- **写隔离**：一阶段提交本地事务前**必须先拿到全局锁**，拿不到就不该提交本地事务；会重试且有超时，超时则回滚本地事务并释放本地锁

追问：全局锁释放时机？官方文档只核到"一阶段提交前获取"，**释放时机未核到原文** → 见核验表。

**Q13. TCC 的三个坑？**

Seata TCC 文档明确点出必须解决 **idempotence（幂等）、empty rollback（空回滚）、hanging（悬挂）**；TCC 不依赖底层数据库，但需要业务实现 Try/Confirm/Cancel，**侵入性强**。

**Q14. Saga / 本地消息表是什么模式？**

- **Saga**：补偿型，每一步配补偿操作（microservices.io *Pattern: Saga*）
- **本地消息表** = **Transactional outbox**（事务性发件箱，microservices.io 同名 pattern）

**Q15. 为什么说 2PC 是「同步阻塞」的？**

一手证据（PostgreSQL 官方文档 `PREPARE TRANSACTION`）：
- *Keep in mind also that **the transaction continues to hold whatever locks it held**.* —— prepare 之后事务不结束，**锁不释放**
- *a prepared transaction will normally be committed or rolled back as soon as an **external transaction manager** has verified that other databases are also prepared* —— 要等协调者第二轮决议才能收尾

→ 所以"同步阻塞"的准确含义：**prepare 之后资源被锁住、必须等协调者（TM）下发 commit/rollback 才能释放**；协调者挂掉期间这些锁一直占着。⚠️「协调者单点」这个说法我没核到一手原文（属教科书结论），见核验表。

> 来源：[RocketMQ 事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)、[Seata: What is Seata (AT)](https://seata.apache.org/docs/overview/what-is-seata/)、[Seata TCC](https://seata.apache.org/docs/user/mode/tcc/)、[Saga pattern](https://microservices.io/patterns/data/saga.html)、[Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)、[PostgreSQL PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html)

## 八、注册中心 / 配置中心（已核验）

**Q16. Spring Cloud Netflix 现在什么状态？**

可核事实：**Spring Cloud 2020.0（Ilford）** release notes 写明——*Spring Cloud Netflix: A number of deprecated modules have been removed. See the wiki for details.*；同版本 Spring Cloud Security 项目被移除、代码并入各项目；负载均衡能力由 **Spring Cloud LoadBalancer** 承担（Spring Cloud Commons 下确实有独立文档页）。

**Q17. Eureka 自我保护到底是什么？阈值多少？**

**阈值原文（Netflix 官方 wiki）**：*If any time, the renewals falls below the percent configured for that value (**below 85% within 15 mins**), the server stops expiring instances to protect the current instance registry information. In Netflix, the above safeguard is called as **self-preservation** mode.*

**代码侧**：服务端 `AbstractInstanceRegistry` 剔除时还有一道上限
```java
int registrySizeThreshold = (int) (registrySize * serverConfig.getRenewalPercentThreshold());
int evictionLimit = registrySize - registrySizeThreshold;
int toEvict = Math.min(expiredLeases.size(), evictionLimit);
```
`PeerAwareInstanceRegistryImpl` 类注释也写明：续约数掉到 `getRenewalPercentThreshold()` 以下、且在 `getRenewalThresholdUpdateIntervalMs()` 周期内 → *eureka perceives this as a danger and stops expiring instances*

→ 所以"自我保护"是**两层**：① 续约率低于 85%（15 分钟窗口）就整体停止剔除；② 即使剔除，单次也有 `registrySize × (1-阈值)` 的上限，防止一次性清空。

**Q18. Nacos 的 AP/CP 在源码里怎么落？**

四个可核事实：

| 事实 | 证据 |
|---|---|
| `Instance` 有 `ephemeral` 字段，默认 `true` | `api/.../pojo/Instance.java` |
| **临时实例走 Distro** | 包名 `naming.consistency.ephemeral.distro.v2.DistroClientDataProcessor`，内部 import `core.distributed.distro.DistroProtocol` |
| **持久实例走 CP 协议** | `PersistentClientOperationServiceImpl` import `com.alibaba.nacos.consistency.cp.CPProtocol` + `core.distributed.ProtocolManager` |
| **CP 实现是 JRaft** | `core.distributed.raft.JRaftProtocol` import `com.alipay.sofa.jraft.Node` |

→ 一句话收口：**Nacos 不是"AP 或 CP"，而是按实例类型分流**——临时实例（默认，走心跳）用自研 Distro 做最终一致（AP），持久实例用 JRaft 做强一致（CP）。

**Q19. Apollo 的长轮询超时是多少？**

源码原文（`BizConfig.java`）：
```java
private static final int DEFAULT_LONG_POLLING_TIMEOUT = 60; // 60s
public long longPollingTimeoutInMilli() {
    int timeout = getIntProperty("long.polling.timeout", DEFAULT_LONG_POLLING_TIMEOUT);
    // java client's long polling timeout is 90 seconds, so server side long polling timeout must be less than 90
    timeout = checkInt(timeout, 1, 90, DEFAULT_LONG_POLLING_TIMEOUT);
    ...
}
```
→ **服务端默认 60s，硬上限 90s**；客户端那边是 90s（注释明说），所以服务端必须更短，才能真正把"挂起→变更即返回"做出来。配置键 `long.polling.timeout`。

**Q20. 注册中心怎么选？（三列都有据）**

| 维度 | Eureka | Nacos | ZooKeeper |
|---|---|---|---|
| 一致性行为 | AP 倾向：续约 <85%（15min）停止剔除，宁可留旧数据 | 按实例分流：临时=Distro(AP) / 持久=JRaft(CP) | 写线性一致（leader+quorum 的 atomic broadcast）；**读不保证线性一致，可能读到旧值** |
| 一致性协议 | — | Distro（自研最终一致）/ JRaft | ZooKeeper Atomic Broadcast（Zab） |
| 健康检查 | 客户端心跳 + 自我保护 | 临时实例心跳 / 持久实例走 CP 写入 | 会话 + 临时节点 |
| 内置配置中心 | ❌ | ✅ 长轮询推送（服务端默认 60s） | ❌ 需自建 |
| 已知短板 | Netflix 模块进维护、2020.0 被移除一批 | 三套协议并存，运维心智成本高 | 读可能旧值；官方明说优先性能而非读一致 |

ZK 那句原文：*Write operations in ZooKeeper are linearizable... Read operations in ZooKeeper are not linearizable since they can return potentially stale data. ... ZooKeeper does this because it prioritizes performance over consistency*

→ **所以"ZK 是 CP"要打个折**：写强一致，读可能旧值。面试被追问"A,B 两台读同一节点值会不会不一样"时，这才是正确答案。

**Q21. Nacos 的配置存在哪几层？**

源码三层，对应三个类：
1. **MySQL（持久层，默认）**：`ExternalDataSourceServiceImpl` 里 `defaultDataSourceType = PersistenceConstant.MYSQL`；MySQL 方言实现 `plugin/datasource/impl/mysql/ConfigInfoMapperByMySql.java`
2. **本地磁盘 dump（快照/容灾）**：`config/server/service/dump/DumpService.java` 引 `ConfigDiskServiceFactory`
3. **内存缓存（读性能）**：`config/server/service/ConfigCacheService.java`

→ 一句话：MySQL 是真相源，磁盘 dump 是重启/断库时的兜底，内存 cache 抗读并发。

## 十、Redis（按面经频次第一，59 次）

**Q29. 为什么说 Redis「单线程」？6.0 之后变了吗？**

`redis.conf` 原文（THREADED I/O 段）：*Redis is **mostly single threaded**, however there are certain threaded operations such as UNLINK, slow I/O accesses and other things that are performed on side threads. Now it is also possible to handle Redis clients socket reads and writes in different I/O threads.*

→ 准确说法：**命令执行仍是单线程**（单线程模型保证原子性与无锁），但 `UNLINK`、慢 I/O 等走后台线程；6.0 起可用 `io-threads` 把 socket 读写并行化。所以「Redis 单线程」这句本身已经不完整了。

**Q30. 单线程为什么还快？**

可核的两点：
1. **I/O 多路复用**：`ae.c` 按性能排序选择事件层 —— *include "ae_evport.c" / ae_epoll.c / ae_kqueue.c / ae_select.c*（优先级 evport > epoll > kqueue > select），单线程即可处理海量连接
2. 纯内存 + 单线程免锁免上下文切换（这条是设计常识，官方未逐字表述）

⚠️ 别背「Redis 6 是多线程所以更快」这种话，I/O 线程不参与命令执行。

**Q31. 内存满了怎么办？淘汰策略有哪些？**

`maxmemory` 触发后按 `maxmemory-policy` 处理，官方 8 种：

| 策略 | 含义 |
|---|---|
| `noeviction` | 不淘汰，写入报错（读仍可用） |
| `allkeys-lru` / `allkeys-lfu` / `allkeys-random` | 全体 key 中按 LRU / LFU / 随机淘汰 |
| `volatile-lru` / `volatile-lfu` / `volatile-random` / `volatile-ttl` | 只在**设置了 TTL** 的 key 中淘汰 |

**关键细节**：原文写明 *The volatile-xxx policies behave like noeviction if no keys have an associated expiration* —— 如果没给 key 设过期时间，volatile-* 系列直接退化成 noeviction，写入报错。这是线上最容易踩的坑。

**Q32. Cluster 是怎么分片的？为什么是 16384 个槽？**

官方原文：*Redis Cluster does not use consistent hashing, but a different form of sharding where every key is conceptually part of what we call a **hash slot**. There are **16384 hash slots** in Redis Cluster, and to compute the hash slot for a given key, we simply take the **CRC16 of the key modulo 16384**.*

→ 面试两个考点：① **不是一致性哈希**（很多人答错）；② 扩容是**迁移 slot**，不是重新分布 key。

**Q33. RDB 和 AOF 怎么选？**

| | RDB | AOF |
|---|---|---|
| 内容 | 数据快照（紧凑单文件） | 命令追加日志 |
| 落盘方式 | 父进程 fork 子进程，*The parent process will never perform disk I/O or alike* | `appendfsync` 控制 fsync 频率 |
| 恢复 | 大数据集下更快 | 重放命令，慢 |
| 丢数据风险 | 两次快照之间全丢 | 见下方三档 |

`appendfsync` 三档（官方原文）：
- `always`：每条命令 fsync，*Very very slow, very safe*
- `everysec`：每秒 fsync，*you may lose 1 second of data if there is a disaster*（**默认推荐档**）
- `no`：从不主动 fsync，交给 OS

**Q34. 主从复制的同步方式？**

官方原文：*Redis uses by default **asynchronous** replication*。主节点不等从节点确认就返回；从节点周期性异步 ACK 已处理位置。→ 所以 Redis 主从是**最终一致**，主挂时可能丢最后一段数据，这也是 Sentinel/Cluster 需要多数派的原因。

**Q35. 缓存穿透 / 击穿 / 雪崩怎么答？**

⚠️ **先说清楚：这三个词不是 Redis 官方术语**，官方文档里没有定义，属国内工程圈叫法。面试官问这题其实在听你能不能把概念-场景-方案对上，所以**回答第一步是给定义**（穿透=查不存在的数据打穿到 DB；击穿=单个热点 key 失效瞬间大量并发；雪崩=大量 key 同时失效或缓存整体不可用）。

可核的原语：`SET key value NX PX`（分布式锁/互斥重建）、RedisBloom 模块（布隆过滤器）。具体方案组合属于架构选型，没有标准答案。

> 来源：[redis.conf（unstable）](https://github.com/redis/redis/blob/unstable/redis.conf)、[ae.c](https://github.com/redis/redis/blob/unstable/src/ae.c)、[Redis 内存淘汰](https://redis.io/docs/latest/develop/reference/eviction/)、[Redis Cluster 分片](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)、[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)、[Redis 复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

**Q36. 循环依赖是怎么解决的？「三级缓存」具体是哪三个？**

## 十二、MySQL / 索引（面经频次 28）

**Q40. 官方到底说 B 树还是 B+ 树？**

MySQL 官方术语是 **B-tree index**（章节名 *Comparison of B-Tree and Hash Indexes*），原文给出它支持的操作：
*A B-tree index can be used for column comparisons in expressions that use the `=`, `>`, `>=`, `<`, `<=`, or `BETWEEN` operators.* 且 `LIKE 'Patrick%'` 能用索引、`LIKE '%Patrick%'` 不能用。

⚠️ 面试常说的「InnoDB 用 B+ 树」是**实现层**说法（数据全在叶子、叶子间有链表），MySQL 官方文档不这么写。安全答法：**「官方叫 B-tree，InnoDB 的实现是 B+ 树形态」**，再讲差别。

**Q41. 聚簇索引 / 二级索引 / 回表**

官方原文（*Clustered and Secondary Indexes*）：
- *Each InnoDB table has a special index called the **clustered index** that stores row data. Typically, the clustered index is synonymous with the primary key.*
- 没有 PK → 用第一个「所有列都 NOT NULL 的 UNIQUE 索引」；都没有 → 生成隐藏的 `GEN_CLUST_INDEX`，用 6 字节 row ID
- *Accessing a row through the clustered index is fast because the index search leads directly to the page that contains the row data*
- 二级索引：*each record in a secondary index contains the **primary key columns** for the row... InnoDB uses this primary key value to search for the row in the clustered index*

→ **「回表」= 二级索引拿到主键值，再回聚簇索引取整行**——这是官方描述的自然翻译，不是官方术语。推论：主键别太长（*If the primary key is long, the secondary indexes use more space*）。

**Q42. 覆盖索引怎么看？**

`EXPLAIN` 的 Extra 出现 **`Using index`** 就是覆盖索引，官方原文：*If the index is a covering index for the queries and can be used to satisfy all data required from the table, only the index tree is scanned. In this case, the Extra column says Using index. An index-only scan usually is faster than ALL because the size of the index usually is smaller than the table data.*

**Q43. 索引下推（ICP）是什么？**

官方原文：*Without ICP, the storage engine traverses the index to locate rows in the base table and returns them to the MySQL server which evaluates the WHERE condition. **With ICP enabled**, and if parts of the WHERE condition can be evaluated by using only columns from the index, the MySQL server **pushes this part of the WHERE condition down to the storage engine**... only if this is satisfied is the row read from the table.*

适用条件（原文）：*ICP is used for the **range, ref, eq_ref, and ref_or_null** access methods when there is a need to access full table rows*，支持 InnoDB 与 MyISAM。

→ 一句话：把能在索引上判断的条件下推到引擎层，**少回表**。

**Q44. 联合索引的最左前缀**

官方原文：*MySQL can use multiple-column indexes for queries that test **all the columns in the index, or queries that test just the first column, the first two columns, the first three columns**, and so on.*，且 *A multiple-column index can be considered a **sorted array**, the rows of which contain values that are created by **concatenating** the values of the indexed columns.*

→ 所以 `(a,b,c)` 上 `where b=1` 用不上；`where a=1 and c=2` 只用得上 a。也解释了两个补充考点：单个联合索引最多 16 列；可以用「哈希列」代替过宽的联合索引。

**Q45. 看 EXPLAIN 该盯哪几个字段？**

官方对 Extra 的说明：
- `Using index` → 覆盖索引（见 Q42）
- `Using where` → *A WHERE clause is used to restrict which rows to match*
- `Using filesort` / `Using temporary` → 官方原话 *If you want to make your queries as fast as possible, look out for Extra column values of Using filesort and Using temporary*（**这两个是主要报警信号**）

> 来源：[Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)、[Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)、[Index Condition Pushdown](https://dev.mysql.com/doc/refman/8.4/en/index-condition-pushdown-optimization.html)、[EXPLAIN Output Format](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)、[B-Tree vs Hash](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)

## 十三、JVM（面经频次 20）

**Q46. 运行时数据区有哪些？**

JVMS §2.5 的官方划分（目录原文）：`pc Register`、`Java Virtual Machine Stacks`、`Heap`、`Method Area`、`Run-Time Constant Pool`、`Native Method Stacks`。

**Q47. 堆和 GC 是什么关系？**

JVMS §2.5.3 原文：*The Java Virtual Machine has a **heap** that is shared among all Java Virtual Machine threads. The heap is the run-time data area from which memory for all class instances and arrays is allocated... Heap storage for objects is reclaimed by an **automatic storage management system (known as a garbage collector)**; objects are never explicitly deallocated.*

→ 关键：JVM 规范**只要求有自动内存管理，不规定怎么实现**（*assumes no particular type of automatic storage management system*）。所以分代、G1/CMS/ZGC 都是 HotSpot 的实现选择——这点能区分「背过八股」和「读过规范」。

**Q48. 双亲委派是怎么描述的？**

`ClassLoader` javadoc 原文：*The ClassLoader class uses a **delegation model** to search for classes and resources. Each instance of ClassLoader has an associated parent class loader. When requested to find a class or resource, a ClassLoader instance will usually **delegate the search... to its parent class loader before attempting to find the class or resource itself**.*

→ 注意官方用词是 **delegation model**（委派模型），「双亲」是中文社区叫法，而且实际是**单亲**（一个 parent）。

**Q49. CPU 100% 怎么排查？**

这是**操作流程**，不是规范内容，命令本身可自测：
1. `top` 找 CPU 最高的 pid
2. `top -Hp <pid>` 找最耗 CPU 的 tid
3. `printf '%x\n' <tid>` 转十六进制
4. `jstack <pid> | grep <hex> -A 30` 定位线程栈

⚠️ 这四步是工程惯例（你 2021 年面经里记的也是这个），没有官方文档背书；回答时要能说出「第 3 步为什么必须转 hex」——因为 jstack 里的 nid 是十六进制。

> 来源：[JVMS §2.5 Run-Time Data Areas](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html)、[ClassLoader.java](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/ClassLoader.java)

## 十四、设计模式在 Spring 里的落点（面经频次 11）

> ⚠️ 前提：GoF 23 种模式出自书，不是规范或官方文档，我无法给「官方出处」。下面只给**Spring 源码里能看到的落点**，模式名称属业界叫法。

**Q50. 单例模式**

Spring 的 singleton 是**容器级单例**（一个 BeanFactory 一个实例），不是 JVM 单例。落点：`DefaultSingletonBeanRegistry.singletonObjects`（见 Q36）。→ 追问「Spring 单例线程安全吗」：容器只保证一个实例，**状态安全要自己保证**（无状态 Bean 天然安全）。

**Q51. 工厂模式：BeanFactory 和 FactoryBean 的区别**

`FactoryBean` javadoc 原文：*Interface to be implemented by objects used within a BeanFactory which are **themselves factories for individual objects**. If a bean implements this interface, it is used as a factory for an object to expose, **not directly as a bean instance** that will be exposed itself.* 且 *the object exposed for bean references (`getObject()`) is always the object that it creates*。

→ 一句话：**BeanFactory 是容器（生产 Bean 的工厂），FactoryBean 是被容器管理的「会造对象的 Bean」**。`getBean("&xxx")` 拿 FactoryBean 本身，`getBean("xxx")` 拿它造的对象。

**Q52. 代理模式**

AOP 的落点见 Q39：有接口 → JDK 动态代理（`JdkDynamicAopProxy`）；`proxyTargetClass` 或无接口 → CGLIB。

**Q53. 观察者模式**

落点：`SimpleApplicationEventMulticaster` —— javadoc 原文 *Multicasts all events to all registered listeners, leaving it up to the listeners to ignore events that they are not interested in.* → `ApplicationEvent` + `ApplicationListener` / `@EventListener` 就是发布-订阅（观察者）在容器里的实现。

**Q54. 模板方法**

落点：`JdbcTemplate` —— 骨架（拿连接、建 Statement、执行、处理异常、释放资源）由模板类固定，变化点用**回调接口**注入（`RowMapper`、`RowCallbackHandler`、`PreparedStatementSetter`）。javadoc 原文提到 *this class is parameterizable by the callback interfaces... there should be no need* 去继承它。→ 顺带一个高频追问：`JdbcTemplate` 是**线程安全**的（*An instance of this template class is thread-safe once configured*）。

## 十五、消息队列（面经频次 9，但几乎每家都追问）

**Q55. Kafka 为什么快？**

官方 Design 文档的三个理由，都能引原文：
1. **Zero-copy（pagecache + sendfile）**：*zero-copy is avoided by allowing the OS to send the data from **pagecache to the network directly**. So in this optimized path, **only the final copy to the NIC buffer is needed***；且 *data is copied into pagecache **exactly once** and reused on each consumption*
2. **顺序写**：*read-ahead and write-behind techniques that prefetch data in large block multiples and group smaller logical writes into large physical writes*（原文还提到顺序磁盘访问在某些情况下比随机内存访问还快）
3. **不用 JVM 堆做缓存**：*The memory overhead of objects is very high, often doubling the size... Java garbage collection becomes increasingly fiddly and slow as the in-heap data increases. As a result... using the filesystem and relying on pagecache is superior*

→ 一句话：**消息落在 OS pagecache，发送时内核直接送到网卡，整个过程只有一次用户态参与**，所以消费者跟得上时磁盘几乎零读。

**Q56. 怎么保证不丢消息？**

Kafka 侧三个旋钮（官方原文）：
- `acks=0/1/all(-1)`：*producers can choose whether they wait for the message to be acknowledged by 0,1 or all (-1) replicas*
- **陷阱**：*"acknowledgement by all replicas" does not guarantee that the full set of assigned replicas have received the message... if a topic is configured with only two replicas and one fails, then writes that specify acks=all will succeed. However, these writes could be lost if the remaining replica also fails.*
- `min.insync.replicas`：*topics have a setting for the minimum number of in-sync replicas that is checked when the producer requests acknowledgment*

→ 正确组合是 **`acks=all` + `min.insync.replicas ≥ 2`**，只设 acks=all 挡不住「只剩一个副本还继续写」。消费端则要**手动提交**（先处理成功再 commit）。

**Q57. 重复消费 / 幂等 / Exactly-Once？**

- **Kafka**：0.11.0.0 起支持幂等生产者 —— *the broker assigns each producer an ID and **deduplicates messages using a sequence number***；配合事务 + `read_committed` 才能做到端到端 exactly-once（Streams 场景）。官方明确：*Kafka guarantees **at-least-once** delivery by default*
- **RocketMQ**：官方直说不能保证不重复 —— *RocketMQ **cannot avoid message duplications (Exactly Once)**, so if the business is very sensitive... de-process at the business level*，做法是用 **msgId 或业务唯一键（如订单号）+ 关系库判重**

→ 面试标准答法：**中间件只保 at-least-once，幂等必须做在消费端**。谁答「用 MQ 保证不重复」直接暴露没落地过。

**Q58. 怎么保证消息顺序？**

⚠️ 这题我没核到官方原文（Kafka「分区内有序」、RocketMQ「同一 MessageQueue 有序」都是社区通行说法，见核验表）。安全框架：**先问清「全局有序还是局部有序」→ 只有单分区/单队列内能保序 → 生产端按业务键 hash 到同一分区 → 消费端单线程消费该分区 → 扩分区就会破坏保序**。

> 来源：[Kafka Design（zero-copy / pagecache / 顺序写）](https://kafka.apache.org/documentation/#design)、[Kafka 消息投递语义（acks / ISR / 幂等 / exactly-once）](https://kafka.apache.org/documentation/#semantics)、[RocketMQ 最佳实践（消费幂等）](https://rocketmq.apache.org/docs/bestPractice/01bestpractice/)

## 十六、网络与操作系统（面经反复出现：三次握手 / TIME_WAIT / NIO / 零拷贝）

**Q59. 为什么是三次握手，两次不行吗？**

RFC 9293 的论证（原文）：*The receiver of the first SYN has no way of knowing whether the segment was an old one or not, unless it remembers the last sequence number used on the connection (which is not always possible), and so it **must ask the sender to verify this SYN**.*

→ 两次握手的问题：**服务端无法确认「客户端确实收到并接受了我的 SYN+ISN」**，历史延迟的 SYN 会让服务端单方面建立连接（资源被占）。第三次 ACK 存在的意义就是让双方都对彼此的 ISN 达成确认。

**Q60. TIME_WAIT 为什么要等 2MSL？**

RFC 9293 状态定义原文：*TIME-WAIT - represents waiting for enough time to pass to be sure the remote TCP peer **received the acknowledgment** of its connection termination request and to avoid **new connections being impacted by delayed segments from previous connections***.

→ 两个目的：① 我发的最后一个 ACK 万一丢了，对方重发 FIN 时我还能回 ACK；② 让旧连接里延迟的报文在网络上自然消失，不会串到复用同一四元组的新连接里。

**Q61. select / poll / epoll 的区别？**

`epoll(7)` 原文：*The epoll API performs a similar task to poll(2): monitoring multiple file descriptors to see if I/O is possible on any of them. The epoll API can be used either as an **edge-triggered or a level-triggered** interface and **scales well to large numbers of watched file descriptors**.*

原理解释（原文）：epoll 实例是内核里的数据结构，对用户态就是两个列表 —— *the **interest list** (the set of file descriptors that the process has registered)* 和 *the **ready list** (the set of fds that are "ready" for I/O)*。

→ 所以 epoll 不用像 select 那样每次把 fd 集合整体拷进内核并线性扫描；**就绪的 fd 直接进 ready list**。ET（边缘触发）只在状态变化时通知一次，必须配合非阻塞 + 循环读到 `EAGAIN`；LT（水平触发）只要就绪就一直通知。

**Q62. 零拷贝到底省了什么？**

`sendfile(2)` 原文：*sendfile() copies data between one file descriptor and another. Because this copying is done **within the kernel**, sendfile() is more efficient than the combination of read(2) and write(2), which would require **transferring data to and from user space**.*

→ 传统 `read + write` 是 4 次拷贝（磁盘→内核缓冲→用户缓冲→socket 缓冲→网卡）+ 4 次态切换；`sendfile` 把「内核缓冲→用户缓冲」这两次省掉。Kafka/RocketMQ/Nginx 静态文件都靠它（Kafka 侧见 Q55）。

> 来源：[RFC 9293 (TCP)](https://www.rfc-editor.org/rfc/rfc9293.html)、[epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html)、[sendfile(2)](https://man7.org/linux/man-pages/man2/sendfile.2.html)、[tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)
